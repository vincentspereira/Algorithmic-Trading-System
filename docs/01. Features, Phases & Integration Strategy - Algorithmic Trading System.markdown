**Algorithmic Trading System**

**System Overview**

This project aims to build a comprehensive, enterprise-grade **algorithmic trading system** from the ground up. The platform's core philosophy is a "Best-of-Breed" integration strategy, selecting the best open-source projects for each major component to create a powerful, modular foundation. The system caters to both non-technical users (via simplicity and no-code options) and professional traders/analysts (via enterprise-grade features), leveraging AI Agents and Agentic AI extensively.

The architecture is designed as a set of distinct microservices that communicate through an **Apache Kafka event bus**. This event-driven approach decouples services, provides data replayability for robust testing, and scales to handle high-frequency data streams for professional traders. The system's standout feature is a sophisticated **Agentic AI Assistant**, which acts as the platform's "brain," enabling users to manage trading, research, and analysis via natural language commands. The core trading engine is **NautilusTrader**, a high-performance, Python-based platform with Rust components, designed for event-driven backtesting and live trading across all asset classes. The Agentic AI Assistant leverages **TradingAgent** for multi-agent decision-making, **OpenBB** for financial data integration, and **TA-Lib/ta-lib-python** (primary wrapper) & **Bukosabino/ta** (secondary wrapper) for technical analysis, forming a robust AI-driven trading brain.

The system incorporates advanced forecasting from **Stock-Prediction-Models** and **LSTM-Neural-Network-for-Time-Series-Prediction**, with real-time predictions enabled by **Real-time-stock-market-prediction** for live trading. **VectorBT** provides GPU-accelerated backtesting, while **backtrader** and **TradingGym** complement NautilusTrader for flexible strategy development and simulated environments. Additional features include portfolio optimisation (**PyPortfolioOpt**, **Riskfolio-Lib**), anomaly detection (**PyOD**), no-code strategy building (**Blockly**), visualisation (**react-financial-charts**, **Plotly Dash**), explainable AI (**SHAP**), reinforcement learning (**FinRL**), and advanced NLP (**Transformers**, **PyTorch**), alongside options analytics (**QuantLib**).

Its flexibility and large community make it perfect for quickly testing a complex custom indicator or a strategy that might be difficult to express in a vectorized way before committing to a full implementation in NautilusTrader.

Do not consolidate to a single tool. Your "Best-of-Breed" integration strategy is your system's greatest strength. By using all four, you create a complete ecosystem that serves different needs:

Here is the step-by-step process of how a user command in Lobe Chat would be executed by OpenHands on the backend.

- - **The Architecture at a Glance**

User -> Lobe Chat (Frontend) -> LangChain Agent (Orchestrator) -> OpenHands Tool (Backend) -> LangChain Agent -> Lobe Chat -> User

- - **Step 1: The User Issues a Command**

The process begins with the user (a developer or analyst) typing a high-level objective into the Lobe Chat interface.

- **User Input:** _"Add a new health check endpoint to our FastAPI service. It should be at the path /api/v1/health and return a JSON object with a status of 'ok'."_
  - **Step 2: Lobe Chat Sends the Command to the Backend**

Lobe Chat's role is simple: it's the messenger. It takes the user's text and sends it as an API call to your central AI backend, which is powered by LangChain.

- - **Step 3: The LangChain Agent Receives and Delegates**

This is the "brain" of your operation. The LangChain agent receives the raw text from Lobe Chat.

- **Intent Recognition:** The agent analyses the prompt and understands that the user's intent is not to run a backtest or query a document, but to perform a _software development task_.
- **Tool Selection:** Because it identified the intent as development, it selects the appropriate tool it has been given: the **OpenHandsTool**.
- **Delegation:** The agent invokes the OpenHandsTool, passing the original user command ("Add a new health check endpoint...") to it for execution.
  - **Step 4: OpenHands Executes the Task (The Core Backend Work)**

This is where the magic happens. The OpenHandsTool is not just a simple function; it's an intelligent agent itself. It operates in two phases: **Planning** and **Execution**.

- **Phase A: The OpenHands Planner**

First, OpenHands takes the high-level goal and, using an LLM, breaks it down into a detailed, step-by-step plan of action. It thinks through the problem and lists the exact terminal commands and code modifications it needs to make.

\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*

**The plan might look like this internally:**

- - 1. **Thought:** I need to find the main file for the FastAPI application to add the new route. I'll start by listing the files in the service directory.

**Action:**

\`ls -R /app/fastapi_service/\`

- - 1. **Thought:** Okay, the main application file seems to be \`/app/fastapi_service/main.py\`. I need to read its contents to understand where to add the new code.

**Action:**

\`read_file('/app/fastapi_service/main.py')\`

- - 1. **Thought:** I will now append the new health check endpoint code to the end of \`main.py\`. The code should define an async function and a route decorator.

**Action:**

\`modify_file('/app/fastapi_service/main.py', code_to_append='

@app.get("/api/v1/health")

async def health_check():

return {"status": "ok"}

')\`

- - 1. **Thought:** The code has been added. The task is complete. I will now report success.

**Action:**

\`finish()\`

\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*\*

- **Phase B: The OpenHands Executor**

Next, the Executor takes this plan and runs each action, one by one, interacting directly with the system's environment (the Docker container's file system and shell). It can:

- Run shell commands (ls, pip install, pytest).
- Read files.
- Write or modify files.

This is a crucial advantage: if step 1 fails (e.g., the file isn't where it expected), the agent can potentially re-plan and try something else.

- - **Step 5: OpenHands Reports Back to the LangChain Agent**

Once the Executor has finished running the plan (or if it fails), the OpenHandsTool returns a final result to the LangChain agent that called it.

- **Example Success Result:** { "status": "Success", "summary": "Successfully added the /api/v1/health endpoint to main.py." }
- **Example Failure Result:** { "status": "Failure", "summary": "Could not find the main FastAPI application file in the expected directory." }
  - **Step 6: The LangChain Agent Informs the User via Lobe Chat**

The LangChain agent takes the structured result from OpenHands and formats it into a natural, human-readable response.

- **Formatting:** It converts the result object into a simple sentence.
- **Response:** It sends the final message back to the Lobe Chat frontend.
  - **Step 7: The User Sees the Final Confirmation**

Lobe Chat receives the response from the LangChain agent and displays it to the user.

- **Final Output in Chat:** _"Task complete. I have successfully added the /api/v1/health endpoint to the service."_

The user never saw the complex plan or the individual commands. They gave one high-level instruction and received one final confirmation, with all the heavy lifting handled seamlessly by the OpenHands agent on the backend.

For example, a stock trading around 10 with ATR of 0.5 is actually more volatile than a stock trading around 200 with a much greater ATR of 2. The Average True Range Percent / ATRP Indicator is a variation of Welles Wilder Average True Range (ATR), which featured in his 1978 book, “New Concepts in Technical Trading Systems.”

It is important to remember that the indicator does not try and predict the direction of price, instead it only tries to define the current volatility in the market. Also, it tries to define current volatility in such a way that it is comparable across all markets, which is the main difference from the traditional ATR. ATR measures volatility at an absolute level, meaning lower priced stock will have lower ATR values than higher price stocks. ATRP displays the indicator as a percentage, to allow for securities trading at different prices per share to be compared.

How this indicator works,

\- ATRP is used to measure volatility just as the Average True Range (ATR) indicator is.

\- ATRP allows securities to be compared, where ATR does not.

When to Use ATRP or Normalised ATR (<https://www.macroption.com/normalised-atr/>):

You should use ATRP (Normalised ATR) instead of the traditional, absolute dollar ATR particularly in these situations:

\- When using ATR for stock screening (to decide which stocks or securities currently have the right volatility for your strategy or trading style).

\- When using ATR as strategy filter (to decide whether the volatility is high enough or low enough to take a signal from a trading strategy, or to “turn on/off” strategies based on market volatility regime).

\- When using ATR to study seasonality or volatility patterns over long periods of time.

\- In general, Normalised ATR is better than traditional ATR in situations which involve comparing different securities or different periods of time.\]
